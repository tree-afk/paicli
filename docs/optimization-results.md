# 优化成果台账｜PaiCLI × SWE-bench Pro V2

这个文件只做一件事：记录**每一次可验证的优化**，给出"改前 → 改后"的同一口径数字，
并标明哪部分能归因给这次改动、哪部分只是采样波动。面试官看这一页就知道改了什么、
凭什么说是改好了；自己回头写简历时也只从这里取数，不凭记忆。

原始数据都在服务器 `runs/` 下（`results.jsonl` + 每条实例的 `agent_trace.json`），
过程与归因细节见 [swebench-optimization.md](swebench-optimization.md)。

---

## 1. 什么时候在这里加一条

加一条的前提是**四件事同时成立**，缺一条就不写进台账：

1. **同口径**：改前改后用同一套判分（逐测试 f2p/p2p）、同一模型、同一 `max_turns`。
2. **单变量**：这一条只改一处（护栏、轮数、判分、网络策略），不同时改两处。
3. **有产物**：结果能从 `results.jsonl` 逐条复现，不靠手抄或推算。
4. **有成对数据**：改前那一轮本身是跑完的（不是中途 API 402 断掉的那种）。

反例（不进台账）：只改了 prompt 试三条、没有改前基线；某条实例突然对了但整轮没跑完；
把两次不同 harness 的结果挨在一起比。

## 2. 填写规则（红线）

- **报 `x/n` 和区间**，不报一个孤零零的百分比。n=20 的 95% Wilson 区间宽约 ±18pp，
  所以 `13/20` 和 `14/20` 的区间是**重叠**的。
- **n < 30 必须标注"不能做显著性结论"**，只当作方向性证据。
- **区分"总变化"和"可归因变化"**：净 +1 不等于"修复带来 +1"，要逐条看翻转方向，
  正向翻转有直接机制解释的才算可归因。
- **不同 harness 版本的数字不能混算**，旧分数要显式标"作废"。
- **不写"提升 X 个百分点"这类句式**（见第 5 节的禁用清单）。

## 3. 条目模板

新条目直接复制这段，填完删掉注释：

```markdown
### E<n> <一句话说明改了什么>（<日期>）

- 改动：<一处改动 + 文件/模块>
- 动机：<改前观察到什么现象，来自哪份 trace>
- 改前：resolved x/n = xx.x%（Wilson [a%, b%]），其它关键指标
- 改后：resolved x/n = xx.x%（Wilson [a%, b%]），其它关键指标
- 可归因：<哪条实例/哪个指标的变化有直接机制解释>
- 不可归因：<哪些翻转属于采样波动，为什么这么说>
- 代价：<tokens / 时长 / 复杂度增加>
- 产物：<runs/... 路径>
```

## 4. 已登记条目

### E1 把 `max_turns` 从 20 提到 30（2026-11-05，禁网，5 条 ansible 子集）

- 改动：只改轮数上限，其余配置不变。
- 动机：20 轮那轮 2 条 `no_patch`，trace 显示不是卡在权限或环境，是"读完了还没落笔"。
- 改前：**3/5 resolved**，平均 17.6 轮，1,369,150 tokens
- 改后：**5/5 resolved**，平均 26.2 轮，3,045,398 tokens
- 可归因：两条失败实例在 30 轮被救回（272,399→707,252、436,609→899,061 tokens），
  机制上是"预算不够读+改+自测"，属确定可归因。
- 不可归因：n=5，只能当方向性结论；且同期对比的"20 轮联网 3/5"与"20 轮禁网 3/5"
  相同，说明这 5 条上网络没带来收益，别把轮数收益说成网络收益。
- 代价：tokens 约 2.2 倍，是明确的成本/正确率权衡。

### E2 修 harness 三处确定性缺陷（2026-11-08，20 条，deepseek-flash，30 轮）

- 改动（全部在 `eval/` 层，没动 `src/paicli` 核心 Agent）：
  1. 命令黑名单从"整条命令子串匹配"改成"按动作单位匹配"（切段、剥 wrapper、认子命令）；
  2. 新增 `create_container_tools()`，让 10 个文件工具把 `/app/...` 归一化到工作区；
  3. prompt 明确"容器无网络、bash 与文件工具看同一个仓库"。
- 动机：逐条读旧跑 20 份 `agent_trace.json`，**90 次**工具调用被判据拒绝
  （黑名单 52 = `ssh` 5、`git remote` 14、`curl` 12、`https/http` 21；`destructive`
  24 = `find /`；路径越界 14）。其中**确定误杀 33 次**：命令层 19（`ssh` 5 次全是
  文件名/循环变量撞词，`git remote` 14 次全是只读的 `git remote -v`）、路径层 14
  （`/app/lib/...` 报 `path escapes workspace`，bash 看得见、文件工具看不见）。
  另有至少 2 次 `https` 拒绝其实是 heredoc 正文里的许可证 URL 被文本扫描误拒
  （`e0c91af4` 写 `py3compat.py`、`0fc6d110` 写 `filepathcategory.py`），所以真实
  联网意图约 31 次。
- 改前：**13/20 = 65.0%**，Wilson [43.3%, 81.9%]；拒绝 90 次
  （黑名单 52、destructive 24、路径越界 14）
- 改后：**14/20 = 70.0%**，Wilson [48.1%, 85.5%]；拒绝 21 次
  （黑名单 2、destructive 19、路径越界 0）
- 可归因：只有 `8127abbc`——旧跑被 `ssh.py` 子串误杀 5 次、f2p 0/15，改后 f2p 全过。
  另外 14 次路径误杀归零，是机制级的确定性变化。
- 不可归因：净 +1 本身（两个 Wilson 区间重叠）；`942424e1`、`bec27fb4` 由 no_patch
  转为 resolved，`1894cb48`、`1a9e74bf` 反向由 resolved 变为 no_patch / not_resolved，
  四条都是采样波动（同模型、`temperature=0` 仍非确定）。
- 代价：无额外开销（tokens 11.15M → 11.29M，基本持平）。
- 产物：`runs/pro_v2_20`（改前）、`runs/pro_v2_20_fixed`（改后）。

### E3 容器 + `--network=none` 替换宿主机 bash（2026-11-06）

- 改动：工具改在任务容器里执行，`--network=none`；容器只挂任务仓库到 `/app`。
- 动机：旧跑 3/7 条实例有访问 gold 补丁/上游提交的 trace 证据，分数不可信。
- 改前：5/7 resolved，但其中 3/7 存在 gold 泄漏访问
- 改后：0 泄漏；旧 5/7 **整轮作废**
- 可归因：泄漏访问 3/7 → 0，是沙箱机制的确定性结果。
- 不可归因：**这不是正确率提升**，是把不可信的分数换掉了。简历里只能写
  "消除了评测泄漏风险"，不能写"正确率提高"。
- 代价：镜像体积与准备时间（20 个逐实例镜像，服务器直连 ghcr 只有 0.18–0.31 MB/s，
  改为本机下载 + 上传 + `docker import` 完成）。

### E4 判分从"退出码"改为逐测试 f2p/p2p（2026-11-06）

- 改动：pytest 写 `--junitxml`，f2p 每条必须 pass（skipped 不算过），p2p 任一 failed
  即回归，全过才 `resolved`；另修掉"空 patch 被误报 patch_apply_failed"。
- 改前：只看 pytest 退出码，一条失败与一片失败同罪，也说不清差在哪。
- 改后：7 条已存 patch 重判，5 条跑通的实例全部满足 `f2p + p2p == collected`（无漏配、
  无重复计数）；`e0c91af4` 从 `not_resolved` 改判 `collection_error`（两个测试模块
  import 即报错）。
- 可归因：判据可解释性——每条实例现在能说"缺哪几条 f2p"。
- 不可归因：正确率数字本身，重判用的是旧 patch，只验证判分器。

### E6 撞顶的 12 条把轮数上限从 30 放到 50（2026-11-08）

- 改动：只改 `max_turns` 30→50，实例集限定为修后跑里 `turns==30` 的 12 条
  （6 条已 resolved、6 条失败），其余配置、模型、harness 全不动。
- 动机：修后 20 条里 12 条撞 30 轮上限，6 条失败**全部**撞顶；需要验证"剩下的
  是预算问题还是能力问题"。
- 改前：**6/12 resolved**，9,051,075 tokens
- 改后：**9/12 resolved**，18,750,340 tokens（**2.07 倍**）
- 可归因：`d6d22519`、`08ac40d0`、`1894cb48` 三条在 30 轮时 `patch_lines=0`
  （一个字都没改），50 轮下写出了能过 f2p 的补丁 → 这三条确实是预算不足。
- 不可归因 / 反例：`4b7ea297` 50 轮仍 `no_patch`（1,840,407 tokens 全花完）；
  `01d1d149` 从 no_patch 变成 not_resolved（有补丁但 f2p 不过）；`1a9e74bf` 40 轮
  仍是 not_resolved。→ 12 条里有 3 条与轮数无关，**轮数不是唯一瓶颈**。
- 代价：tokens 2.07 倍；已 resolved 的 6 条里 4 条把 50 轮全部花完（只有
  `bec27fb4` 28 轮、`1af602b2` 23 轮提前收手），说明"多给预算"不能替代
  "知道什么时候该停"。
- 产物：`runs/pro_v2_20_fixed_t50`（其中 `4b7ea297` 首跑遇到一次 API 瞬断，
  记 `infra_error` 后单独补跑，最终行取补跑结果）。
- 口径提醒：这是**12 条子集**的对照，不能把 9/12 直接加到 20 条总分上。
  要得到"20 条统一 50 轮"的正式数字，还得把另外 8 条也重跑。

### E7 拒绝文案改为"隐藏测试不可达" + 第 3 次翻查给硬提示（2026-11-08）

- 改动（只在 `eval/container_bash.py`，没动 `src/paicli`）：
  1. 所有策略拒绝的返回文本固定附带：容器无网络、无上游仓库，隐藏测试 / gold
     patch / 未来提交都不可达，不要在 `/app` 外搜索，用手上的代码改完收尾；
  2. 按实例统计"翻答案"动作（`find /`、读 `/app` 外的 `ls/cat/grep`、`pip cache/show`、
     `git log/rev-list/branch/tag --all`、`git cat-file/fsck/show-ref`、`curl/wget` 等）；
     第 3 次起在同一工具结果里追加带次数的硬提示；计数挂在工具实例上，不跨实例。
- 动机：读 50 轮的 trace，已 resolved 的 4 条里翻查 8/9/10/5 次；`4b7ea297` 19 次、
  `01d1d149` 26 次。旧拒绝文案只有 `command rejected by policy: curl`，模型会换写法重试。
- 改前（`runs/pro_v2_20_fixed_t50`，12 条 × 50 轮）：**9/12 = 75.0%**，
  Wilson [46.8%, 91.1%]；tokens 18,750,340；bash 659 次；翻查 174 次；提示 0 条。
- 改后（`runs/pro_v2_20_fixed_t50_hint`，同 12 条 × 50 轮）：**11/12 = 91.7%**，
  Wilson [64.6%, 98.5%]；tokens 15,023,025（**-19.9%**）；bash 564 次（-14.4%）；
  翻查 49 次（**-71.8%**）；10/12 条共触发 26 次硬提示；无 resolved → 失败的反向翻转。
- 可归因：提示确实送达并改变行为——26 次硬提示、翻查动作确定性下降；两条翻正
  `4b7ea297`（no_patch → resolved，f2p 24/24）与 `01d1d149`（not_resolved →
  resolved，f2p 3/3）恰好是改前翻查最多的两条；所有 resolved 条 f2p 全过、p2p 无回归。
- 不可归因：9/12 → 11/12 本身（12 条子集、Wilson 区间重叠，属噪声）；
  `1a9e74bf` 翻查 14 → 5 次但仍 f2p 0/4，说明"停止翻答案"不等于"会修"。
- 代价：无额外开销（tokens 反降 20%）；个别实例少试探后反而变慢（`bec27fb4`
  28→29 轮、`08ac40d0` 43→48 轮、tokens 微升），属采样波动。
- 产物：`runs/pro_v2_20_fixed_t50_hint`（改前为 `runs/pro_v2_20_fixed_t50`）。

### E8 补跑未撞顶的 8 条，得到"20 条统一 50 轮"（2026-11-08）

- 改动：把 30 轮时未撞顶的 8 条（30 轮下已全部 resolved）用**当前 harness**
  （含 E7 提示）、`max_turns=50` 重跑，补齐统一口径。
- 动机：E6/E7 都是 12 条子集，不能并入 20 条总分；简历上的正式数字需要一份
  "同一模型、同一 harness、同一轮数"的 20 条完整跑。
- 改前（30 轮，修后 harness 无提示）：14/20 = 70.0%，Wilson [48.1%, 85.5%]，
  11,285,166 tokens
- 改后（50 轮，当前 harness）：**19/20 = 95.0%**，Wilson [76.4%, 99.1%]，
  17,595,313 tokens（1.56 倍）
- 8 条子集：**8/8 resolved**，全部在 8–35 轮内提前收手、无一撞 50 轮；
  tokens 2,572,288；翻查 16 次、硬提示 7 次（`43f9e7e0` 占 5 次，仍 35 轮通过）。
- 可归因：这个子集对"抬轮数"没有信息量——30 轮本来全过，50 轮仍全过，
  只是把正式口径补齐。
- 不可归因：19/20 与 14/20 的差。它混了三件事（30→50 轮、E7 提示、采样波动），
  且两个 Wilson 区间在 76.4–85.5% 重叠，**不能**说成"优化后提升 25 个百分点"。
  单变量证据看 E6（只改轮数）与 E7（只改提示）。
- 代价：tokens 1.56 倍（平均每条约 88 万）；唯一失败仍是 `1a9e74bf`（f2p 0/4）。
- 产物：`runs/pro_v2_20_fixed_t50_rest`（8 条）+ `runs/pro_v2_20_fixed_t50_hint`
  （12 条），合并即 20 条统一 50 轮。

## 5. 简历 / 面试口径

可以写（每条都能被代码和 `runs/` 复现）：

- 为 Coding Agent 搭建容器化评测 harness（20 条 SWE-bench Pro V2 实例、逐测试
  f2p/p2p 判分、补丁与工具轨迹全量落盘）。
- 通过 trace 归因定位工具层 33 次确定性误杀（命令层 19、路径层 14），把判据拒绝
  从 90 次降到 21 次、路径误杀归零，同一模型同一轮数下 resolved 13/20 → 14/20。
- 用 20/30 轮消融定位轮数预算是主要瓶颈（5 条子集 3/5 → 5/5，tokens 2.2 倍），
  形成明确的成本/正确率权衡结论。
- 用 trace 定位"翻隐藏测试/答案"是主要浪费（12 条子集里翻查 174 次），把拒绝文案
  改成明确不可达 + 第 3 次翻查给硬提示后，同 12 条同 50 轮下翻查 174 → 49 次、
  tokens 降 20%，resolved 9/12 → 11/12。
- 当前 harness 在 20 条 SWE-bench Pro V2 实例、统一 50 轮下 resolved 19/20
  （95.0%，Wilson [76.4%, 99.1%]），唯一失败为 f2p 0/4 的 `qutebrowser-1a9e74bf`。

禁止写（面试官一追问就站不住）：

- ~~"准确率提升 5 个百分点"~~ —— 13/20 与 14/20 的 Wilson 区间重叠，属噪声。
- ~~"修复后模型变强了"~~ —— 同模型，改的是工具与提示，且反向翻转同样存在。
- ~~"评测准确率 70%"~~ —— 必须带 `14/20`、模型名、轮数、判分口径。
- ~~把作废的 5/7 或泄漏那轮的任何数字拿出来用~~。
- ~~把 9/12 → 11/12 说成显著提升~~ —— 12 条子集、区间重叠；能说的只有机制层
  "翻查调用 174 → 49、tokens -20%"和两条具体实例的翻转。
- ~~"优化后从 70% 提到 95%"~~ —— 19/20 与 14/20 混了轮数与提示两项改动，且区间
  重叠；19/20 只能作为"当前 harness + 50 轮"的成绩，不是某一项优化的效果。
